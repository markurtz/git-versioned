# Version sources, templates and post releases

Where the version comes from when tags are not the whole story, how dev and
nightly versions are spelled, what the generated version module holds, and how a
post release fixes packaging without a new version.

| Level        | Shows                                                                                                      | Needs |
| ------------ | ---------------------------------------------------------------------------------------------------------- | ----- |
| Intermediate | `version = "branch"`, `"commit"`, `"file:…"`, `"python:…"`, `formats`, `module_template`, `release --post` | git   |

## Run

Copy this folder anywhere and run the commands below in it. The transcript is
checked on every test run, so it is exactly what you will see, apart from
hashes and dates.

### The version from a branch, a commit, a file or a function

`version` names the source. `branch` and `commit` read an `X.Y.Z` from the
branch name or the latest commit subject, and fall back to tags when there is
none. `file:PATH` reads the first `X.Y.Z` in a file, and `python:MODULE:FUNCTION`
calls a function in the project.

```console
$ git init -q && git add -A && git commit -qm "feat: first release" && git tag v1.0.0
$ git switch -q -c release/1.4.0 && GITVERSIONED__VERSION=branch gitversioned version
1.4.0
$ git switch -q main && GITVERSIONED__VERSION=branch gitversioned version
1.0.0
$ git commit -q --allow-empty -m "chore: prepare 2.1.0" && GITVERSIONED__VERSION=commit gitversioned version
2.1.0
$ echo 3.0.1 > VERSION && GITVERSIONED__VERSION=file:VERSION gitversioned version --explain | grep note
note      version 3.0.1 from VERSION
$ GITVERSIONED__VERSION=python:release_info:version gitversioned version
4.2.0
$ GITVERSIONED__VERSION=python:release_info gitversioned version
fail  invalid config in defaults: `version` 'python:release_info' must name a function: python:MODULE:FUNCTION
[exit 2]
$ rm VERSION && git reset -q --hard v1.0.0
```

[`release_info.py`](release_info.py) holds the function. A source sets the
version the way a pin does, so `version --write` and builds use it.

### Version templates

`formats` spells dev and nightly versions with `{next}`, `{base}`,
`{distance}`, `{date}`, `{sha}` and `{branch}`; the result must be a valid
PEP 440 version.

```console
$ git commit -q --allow-empty -m "fix: one" && git commit -q --allow-empty -m "fix: two"
$ gitversioned version
1.0.1.dev20261125+ca3beed
$ GITVERSIONED__FORMATS='{"dev": "{next}.dev{distance}"}' gitversioned version
1.0.1.dev2
$ GITVERSIONED__FORMATS='{"nightly": "{next}.dev{date}"}' gitversioned version --type nightly
1.0.1.dev20261125
$ GITVERSIONED__FORMATS='{"dev": "{next}-{nope}"}' gitversioned version
fail  formats.dev '{next}-{nope}' has an unknown placeholder: 'nope'. Use {next}, {base}, {distance}, {date}, {sha}, {branch}.
[exit 2]
```

`module_template` replaces the generated `version.py` with your own
[`string.Template`](https://docs.python.org/3/library/string.html#template-strings)
file, here [`version.tmpl`](version.tmpl):

```console
$ GITVERSIONED__MODULE_TEMPLATE=version.tmpl gitversioned version --write
...
$ cat src/demo/version.py
# Generated by gitversioned. Do not edit.
VERSION = "1.0.1.dev20261125+ca3beed"
VERSION_INFO = (1, 0, 1, 'dev20261125', 'ca3beed')
TAG = "v1.0.0"
```

### Post releases

A post release ships the same code again, for a packaging fix. `release --post`
plans the next post release of the latest release, spelled `1.0.0.post1` and
tagged `v1.0.0.post1`; SemVer shows it as build metadata.

```console
$ git restore src && git reset -q --hard v1.0.0 && git commit -q --allow-empty -m "build: fix the sdist contents"
$ gitversioned release --post | head -2
release   1.0.0.post1  (set by --post, from 1.0.0)
tag       v1.0.0.post1
$ gitversioned release --post --write | tail -1 && git commit -qam "release: v1.0.0.post1" && gitversioned release --tag
Wrote CHANGELOG.md.
tag       v1.0.0.post1 at ..., created locally
$ gitversioned version && gitversioned version --standard semver
1.0.0.post1
1.0.0+post.1
$ gitversioned release --post --json | grep '"version"'
  "version": "1.0.0.post2",
```

## How it works

- Sources and templates are settings like any other: in `gitversioned.toml`,
  `[tool.gitversioned]` or `GITVERSIONED__*`. The
  [configuration guide](https://markurtz.github.io/git-versioned/guides/configuration/)
  lists every placeholder.
- A post release sorts after its release and before the next one, so
  `1.0.0 < 1.0.0.post1 < 1.0.1`. Its changelog section is `## [1.0.0+post.1]`.
